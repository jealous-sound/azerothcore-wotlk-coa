##################################
# Module: mod-coa-change-potions
##################################

## The CoA change potions, restored as one module

Nine change potions exist in the realm's own data and in the client's item cache - Customization
(200000, 910201, 2001185), Race Change (200001, 2001181), Faction Change (910200, 505005, 505006)
and Class Change (97858) - and not one of them had an `item_template` row in this repository. Three
of them were already sold from Tiraxis's convenience list by mod-ethereal-bazaar's generated rows, so
those three slots came up empty on a realm built from this tree; the other six had no source at all.

`modules/mod-coa-change-potions` is the whole restoration, and it is one module because the nine
items are one family.

**The two halves that already existed.** The client and the core implement the three character-select
services completely: `Player::BuildEnumData` writes the Customize / Race Change / Faction Change
buttons from the at-login flags of `characters.at_login` (`AT_LOGIN_CUSTOMIZE`,
`AT_LOGIN_CHANGE_RACE`, `AT_LOGIN_CHANGE_FACTION`), and the core's own handlers apply the change with
every check a paid service gets. The module only has to raise the flag the client reads.

**The half that did not.** Nothing in the client or the core can change a class: the client's paid
services are exactly three, its opcode table has no class-change opcode or button, and the core has
no class-change path at all. The live realm's class change ran on Ascension's own core, so its
"which class" step is not recoverable - the module supplies it.

### What the module does

* **The choice.** The Class Change Potion opens an item gossip menu (`ItemScript::OnGossipSelect`,
  reached through `item_template.ScriptName`, the path `AscensionBankVoucher.cpp` uses) listing the
  classes character creation offers, in creation's own order and under its own names: the client's
  own creator is the list, `Interface\GlueXML\CharacterCreate.lua` orders its pages by
  `COA_CLASS_ORDER` and labels each with the name `ChrClasses.dbc` gives the id. A class the race
  cannot be, and the class the character already is, are left out; the availability test is
  `sObjectMgr->GetPlayerInfo(race, class)`, which this repository already treats as the
  authoritative list. The menu's text is one plain `npc_text` row.
* **The conversion.** The pick rebuilds the character as the class it would be if it had been
  created as that class at level one and leveled to the level it is, read from the realm's own
  definitions of a class: `AscensionLiveBaseline` spells, proficiencies and skills (what
  `InitializeLiveBaseline` builds inside `Player::Create`), `playercreateinfo_spell_custom` and
  `playercreateinfo_skills`, `AscensionCompatData::ClassSpells` with `ascension_custom_class_spell`,
  `AscensionProgression::Ranks` and `AscensionCompatData::CoATalentEntries`. Those are read twice,
  and the two readings answer different questions: at the character's level they say what the class
  accounts for, which bounds what may be **taken away**; at level one they say what the class **is**,
  and only that is handed out. A level 50 character keeps level 50 and receives the abilities,
  proficiencies and skill lines creation would have built for the class - no spells or ranks the
  ladder would have given them by this level, no talent allocated. That progression is the player's
  to buy afterwards, exactly as it would have been on a character that started this class at level
  one.
* **No hybrid state.** Every class-owned spell the new class does not account for is removed with
  its auras, whichever class brought it, and the same for class-owned skill lines and proficiencies;
  glyphs, talents, the chosen specialization and every stored build are cleared; a pet summoned by
  the old class is dismissed; class-only equipment the new class cannot use moves into the bags
  (never destroyed, and it stays equipped and is logged if there is no room). Removal is bounded by
  the union of every class's definitions rather than by the class being left, so `A -> B -> C -> A`
  ends where `A -> A` would have and nothing accumulates. Professions, quest rewards, mounts,
  item-granted spells and racial abilities belong to no class and are never touched. Level,
  experience, identity and every other non-class progression are carried over untouched.
* **The end of it.** Both the service potions and the class potion log the character out to the
  character screen ten seconds later, because that is where the next step happens: the core's own
  instant logout (`SMSG_LOGOUT_RESPONSE` with `Instant`, then `WorldSession::LogoutPlayer`). The
  countdown runs on the world thread in `WorldScript::OnUpdate`, not on a map event - a map-thread
  logout tears the player out of the map in the middle of its own update. Re-drinking inside the ten
  seconds resets the countdown instead of queueing a second logout, and a player who left in the
  meantime is skipped.
* **The notices.** One line to the middle of the screen and one to the chat log, in the realm's
  notice yellow with a single accent colour for the words the player acts on: the ten seconds and
  the button are `|cffffb340` amber, and the class potion's notice paints the class in the class's
  own colour. The accent is `ChangePotions.NoticeAccent`, read when a notice is sent. The chat copy
  carries the potion as a real clickable item link. A potion is refused, and not spent, in combat or
  while another service is already pending.

### How to upgrade

Rebuild the worldserver and let the updater apply the two `rev_20260927_1*` files (or run them by
hand). Both are idempotent - the item rows are `REPLACE INTO` and the menu text is `DELETE` +
`INSERT` - and both were applied twice against a live world database with every row read back
identical. Nothing else is required: no core file is touched, the module is picked up from
`modules/`, and its configuration ships with it. Tiraxis's convenience list fills its three empty
slots on its own once the rows exist.

### What to test in game

* `.additem 910201`, `.additem 200000` or `.additem 2001185`: drink one - the notice appears once,
  the potion leaves the bag, and ten seconds later the character screen offers **Customize**.
* `.additem 200001` (or `2001181`) and `.additem 910200`: the same for **Race Change** and
  **Faction Change**. `505005` on an Alliance character and `505006` on a Horde one do the same for
  the faction-restricted pair.
* `.additem 97858`: the menu lists the classes creation offers, in creation's order; picking one
  spends the potion, prints "You are now a ..." with the class in its own colour, and ten seconds
  later the character list shows the new class. After logging in the character has the new class's
  level-one abilities, proficiencies and skill lines and its own starting action bar, with no spell
  or talent of the old class, no specialization and no glyphs.
* Run the chain `A -> B -> C -> A` at a fixed level: the third arrival has to read the same as the
  first, with the same counts on the worldserver's own line (`changed class X -> Y at level N: ...
  class spells and ... skill lines removed, ... spells of the new class granted, ... item(s)
  unequipped, talents and specialization reset.`). The granted count is the level-one count and does
  not grow with the level.
* Try the refusals: drink a potion in combat, drink a second service potion while one is pending,
  and open the class menu and then discard the potion before picking - the class must not change.
